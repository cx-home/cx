    WebAssembly Target

    WASM is the long-term distribution target. C ABI is the current mechanism. The boundary moves, the contract stays.

    Why WebAssembly

    CX ships today as a native C ABI library — libcx.dylib on macOS, libcx.so on Linux — that every binding loads through its own foreign-function machinery ctypes for Python cgo for Go koffi for TypeScript P/Invoke for C# JNA for Java/Kotlin FFI gem for Ruby swift-c for Swift bindgen for Rust. It works and it is fast, but it carries two ongoing costs. Every supported triple needs a binary; every binding carries its own FFI plumbing. A WebAssembly target collapses both.

    The long-term distribution target is a single libcx.wasm artifact loaded by each binding through its host runtime — wasmtime, wasmer, the browser, Node, V8, Wasmer-Python. The function names, the binary wire protocol, and the per-language Document API all stay the same. The boundary moves; the contract stays.

    What the C ABI Gives Us Today

    • libcx compiled to a platform-specific .dylib or .so
    • include/cx.h exporting ~49 functions (the full surface)
    • Per-language FFI binding (ctypes, cgo, extern "C", koffi, P/Invoke, JNA, FFI, swift-c)
    • Platform binaries: macOS arm64 + Linux x86_64 today; per-triple expansion as bindings need them

    What Changes With WebAssembly

    The shape of the artifact and the loader change. The function surface does not.

    • libcx compiles to libcx.wasm — one portable binary, no per-triple build matrix
    • No per-language FFI setup; each binding loads the WASM module through the host runtime instead
    • Memory crosses linear-memory boundaries: caller writes the input string into WASM linear memory, reads the output back out, calls cx_free in the module
    • Same function names, same → char* contract — projected onto linear-memory offsets

    What Stays the Same

    The contract is what matters; the loader is implementation.

    • Every function name and semantic — the ~49-entry surface in include/cx.h
    • The ast-bin wire protocol — byte-identical, untouched by the loader change
    • The data-bin format and Arrow C-Data ABI — same bytes, same chunked-column semantics
    • The Document API in each binding — native data structures over the same wire bytes, unaffected
    • The error contract per language — same conventions, same code surface

    Per-Binding Changes When WASM Lands

    Catch-up is a binding-level swap, not a rewrite. Four steps per binding.

    • Replace the FFI loader (ctypes / cgo / koffi / P/Invoke / JNA / FFI gem / swift-c) with a WASM runtime loader for that language
    • Replace direct memory pointers with read/write against the WASM linear-memory buffer
    • Keep the binary decoders unchanged — ast-bin and data-bin payloads carry the same bytes
    • Keep the Document API implementation unchanged — it operates on the decoded tree, not on the FFI boundary

    Status

    libcx-wasm is not yet built. The C ABI is the only distribution mechanism on v0.7.0; the WASM target is tracked for the v0.7.x window. A reference WASM build will land alongside a parity-tested rollout across the 10-binding matrix — until that point, bindings MUST link against the C ABI and SHOULD NOT assume the WASM artifact exists. The playgrounds and live-eval scenarios that reference libcx-wasm in their messaging are forward-looking; they fall back to canned outputs today.

    Track concrete progress in the GitHub repo. When libcx-wasm reaches a usable artifact, the Playground page swaps its lookup-table evaluator for the live module without changing the page UI.
