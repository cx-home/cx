    Analytics, columnar formats, and bridges

    The analytics lane

    CX has an analytics lane. The same brackets that carry a config file also carry a typed columnar table; the same canonical-bytes-plus-hash identity that anchors a single document also anchors a billion-row dataset; the same evaluator that templates a Markdown report also streams over a multi-gigabyte file in bounded memory. The lane has three load-bearing pieces, and this section is about how they compose.

    The three pieces are: a logical data shape (the [table[…]] block, with typed columns and nullable cells); a physical wire format (CXCol, the column-oriented streaming binary form, tag 0x63 in spec/core/data-bin.md §3.11); and bridges to the broader ecosystem (Apache Arrow C Data Interface for zero-copy interop, Apache Parquet for cross-tool storage).

    • Logical: [orders [table[id::int customer::string]] …] — see table-shape. Authored in CX text, parses into the same AST as any other CX element, validates against .cxs schemas, hashes via SHA-256 over canonical bytes.
    • Physical: CXCol — the column-oriented streaming binary form. Row-group chunked, optionally zstd-compressed per chunk, optionally schema-driven for tag-density. See cxcol.
    • Bridges: Arrow C Data Interface (zero-copy in-process handoff) and Parquet (cross-ecosystem storage). See arrow-bridge and parquet-bridge.
    • Streaming: the CX streaming evaluator (see spec/core/streaming.md) emits StartTable / RowGroup / EndTable events over CXCol data, so directives like [?for] and [?modify] can operate on tables that don't fit in memory.
    • Identity: CXCol files have a stable SHA-256 over their canonical (uncompressed) bytes. Compression level does not change the hash. Chunk boundaries do — see cxcol-identity for the rule.

    The rest of this section walks each piece. The normative spec documents are spec/core/data-bin.md §3.10-3.13 (wire format) and spec/misc/table-api.md (host binding API). This guide is the working developer summary.

    Naming. CXCol is the column-oriented streaming format name. The CXDB / CXDatabase namespace is reserved for a future query-engine product and does not refer to the file format. Throughout this guide, CXCol is the format; .cxbin is the file extension (.cxcol is a deprecated alias, recognized read-only — spec/process/governance.md §12.2); the cx_table_* prefix appears on the C ABI streaming identifiers (spec/core/abi.md §2.10).

    The [table[…]] data shape

    The [table[…]] clause-child opener declares a typed columnar table at the logical CX layer. It is a CX element like any other — same brackets, same parse rules, same canonical-bytes contract — but the parser recognizes the glued [table[ opener (grammar [29]) and produces a Table value rather than a generic element. The element's own name is the table's name.

          [orders [table[id::int customer::string amount::float ts::datetime]]
           1 Ada   42.50 2026-05-22T10:00:00Z
           2 Grace 17.25 2026-05-22T10:15:00Z
           3 Linus 99.00 2026-05-22T11:30:00Z]

    The [table[…]] clause carries the column spec: whitespace- separated name::type entries, where an entry without a type ([table[a b c]]) declares a string column. The body is a flat run of whitespace-separated cells, partitioned into rows by the column count (grammar [29c] — each row supplies exactly one cell per column). A cell that cannot carry the declared column type refuses loudly rather than coercing — the encode-refusal rule of spec/core/data-bin.md §3.10.3 (never wrap, never widen, never approximate).

    Supported column types match the CX scalar type system: int and the sized integers (i8–i64, u8–u64), bigint, float and the reduced widths (f32, f16), decimal, bool, string, bytes, date, and datetime. The full type catalog with byte encodings is in spec/core/data-bin.md §3.10.3 + spec/misc/type-mapping.md.

    Null cells

    Any column can carry null cells. A null cell is written as the literal null — a bare token in cell position; empty cells are not allowed in the wire form.

            [customers [table[id::int name::string phone::string]]
             1 Ada   '555-1212'
             2 Grace null
             3 Linus '555-9999']

    On the wire, a column with null cells uses the nullable wrapper of spec/core/data-bin.md §3.10.5: type code 0x80, then the inner type code, then a null bitmap of ceil(rows/8) bytes (bit set = null), then the packed payload of the non-null cells only. The host binding's Table.cell(r, c) returns the host's null sentinel (None in Python, nil in Go, Option::None in Rust).

    Dictionary encoding

    Dictionary encoding is an opt-in container form — tag 0x62 in spec/core/data-bin.md §3.10.2. Each column's payload starts with a marker: plain (the §3.10.3 layout) or dictionary-encoded (distinct values in insertion order, then one varint index per row). Decoders rebuild the values transparently; the host-binding API never exposes the indices.

    Canonical writers emit the plain 0x60 form. A writer that opts into 0x62 uses a dictionary for a column only when the dictionary actually saves bytes — the canonical constraint of §3.10.2, evaluated per column — so categorical data (status, region, type) dictionary-encodes and high-cardinality data stays plain. CXPath = and [?match] value comparison operate on the decoded value, so user code is dictionary-agnostic.

    Schema validation

    Tables validate against .cxs schemas the same way ordinary elements do — the table block is an element, and the schema language of spec/core/schema.md applies to it as to any other element. See [[data#schema]] for the schema language. At the binary layer, a CXCol file can carry a schema reference that names its schema by content hash (see cxcol-schema-driven).

    The Table host-binding API

    Bindings expose a Table value type for [table[…]] blocks. Methods match across bindings up to host-idiom differences; the canonical surface is documented in spec/misc/table-api.md.

            import cxlib
           t = cxlib.Table.from_cx(open('orders.cx').read())

           print(t.cols)         # ['id', 'customer', 'amount', 'ts']
           print(t.types)        # ['int', 'string', 'float', 'datetime']
           print(t.row_count)    # 3
           print(t.row(0))       # {'id': 1, 'customer': 'Ada', ...}
           print(t.column('amount'))  # [42.5, 17.25, 99.0]

           # Slicing / projection
           sub = t.head(2).select_cols(['customer', 'amount'])
           print(sub.to_cx())

    The canonical surface (spec/misc/table-api.md §3) is: the cols / types / row_count / col_count properties; the row / column / col_at / cell / cell_by_name accessors; the slice / head / tail / select_cols projections; row iteration; and the to_cx / to_csv / to_json / to_data_bin / to_dict_list conversions. The same shape exists in V, Python, Go, and Rust with the naming conventions of each host.

    CXCol — column-oriented streaming format

    CXCol is the physical wire form for tabular data: column-oriented, row-group-chunked, content-addressable, and streamable in bounded memory. The data-bin tag is 0x63; the file extension is .cxbin. The normative byte-level layout is in spec/core/data-bin.md §3.11.

    The format is a single sequential pass: header, column spec, then a stream of row groups, then a terminator. Writers emit one row group at a time and can produce a billion-row table in memory bounded by the largest row group. Readers pull row groups one at a time and can skip groups by their length prefix without decoding them.

    Wire layout

    A CXCol stream is:

    • 12-byte header. Magic CXCol (5 bytes, 0x43 0x58 0x43 0x6F 0x6C), version byte (0x01), flags byte, max_depth (uint32 LE), reserved byte. Flag bit 0 is endianness (1 = little-endian); flag bit 1 signals schema-driven mode (see cxcol-schema-driven); bits 2–7 are reserved and must be zero.
    • Column spec. The chunked-table tag 0x63, then uvarint(col_count), then one col-spec per column — the column name as a tagged string plus its type code (the §3.10.1 shape). Declared once at the head — every row group in the file conforms to this spec.
    • Row-group sequence. Each group is uvarint(body_byte_len) <body-tag> <body>. body-tag 0x01 = plain (uvarint(row_count) then column-major buffers); 0x90 = the zstd page-compression wrapper (§3.12), whose decompressed bytes form the same plain body.
    • Terminator. A single 0x00 byte (a zero-length row group) closes the stream.

    The 2²⁰ (1,048,576) rows per group is the canonical chunk size — cx canonical and cx hash re-chunk a CXCol input to it, and writers targeting cross-system hash invariance should use it. Different chunk sizes produce valid CXCol files but with different SHA-256 hashes.

    Content-addressable identity

    A CXCol file's SHA-256 hash is computed over its canonical uncompressed bytes — the bytes you would see if every 0x90 page-compression wrapper were unwrapped to its 0x01 plain form. Compression is a transport / storage choice; identity is a content choice; the format keeps them orthogonal.

    • Same data + same chunking + same schema → same hash, regardless of zstd level or whether compression was applied at all.
    • Different chunk size → different hash. Chunk boundaries are part of the canonical form. The 2²⁰-rows-per-group convention is the cross-writer interoperability rule.
    • Hash composes with hash. The same SHA-256 primitive that hashes a CX document hashes a CXCol file — tooling pipelines (caching, dedup, signing, content-addressable storage) treat both uniformly.
            import cxlib
           # Framed CXCol chunked-table bytes: [u32 LE size][CXCol payload]
           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())
           # The payload's identity is the SHA-256 of its canonical
           # (uncompressed) bytes: a 0x90-compressed row group unwraps
           # to its 0x01 plain form before hashing, so the compression
           # level never moves the hash.

    Streaming reader / writer

    The streaming surface is the C ABI reader / writer family in spec/core/abi.md §2.10 (capability bit 21): cx_table_reader_open / cx_table_reader_open_fd / cx_table_reader_schema / cx_table_reader_next / cx_table_reader_close, and cx_table_writer_open / cx_table_writer_open_fd / cx_table_writer_emit_row_group / cx_table_writer_close_get_bytes / cx_table_writer_close. The Python binding wraps the family as cxlib.TableReader / cxlib.TableWriter.

            import cxlib

           framed = cxlib.to_data_bin_chunked(open('big.cx').read())

           # Reader — pulls one row group at a time
           with cxlib.TableReader(framed) as r:
               spec = r.schema()          # col-spec payload bytes
               for group in r:            # row-group payloads, one at a time
                   process(group)

           # Writer — pushes one row group at a time
           with cxlib.TableWriter(spec) as w:
               for group in source_of_groups():
                   w.emit(group)          # bounded memory per group
               framed_out = w.close_get_bytes()

    Go and Rust reach the same reader / writer handles through the shared C ABI directly — the §2.10 symbol family is the contract; a packaged native wrapper in those bindings has not shipped yet.

    Memory budget is one row group in flight per stage in the pipeline. A reader chained into a CXPath filter chained into a Parquet writer holds three row groups at once, total — regardless of the table's logical row count. See streaming for the directive-level view.

    Schema-driven mode

    When the writer knows both sides of the wire have access to the schema, header flag bit 1 enables schema-driven mode: per- value type tags are omitted for values the schema declares; reader and writer walk the schema in lockstep with the data. Wire density approaches Parquet's typed encoding.

    Schema-driven mode is opt-in — cx_to_data_bin --schema-driven at the ABI, cxlib.to_data_bin_schema_driven(…) in Python; having a schema in scope does not silently promote the encoder. The schema reference forms (0x10 content-hash, 0x11 inline, 0x12 content-hash + name hint, 0x13 self-describing multihash) are documented in spec/core/data-bin.md §3.13.1; the cx table subcommand resolves --schema-from= arguments to a content hash before emit.

    Schema-driven mode requires the reader to retrieve the schema by its content hash. Local lookup is the default; the callback-shaped content-store ABI is a planned follow-up.

    Arrow bridge — zero-copy interop

    CXCol bridges to Apache Arrow via the Arrow C Data Interface — a struct-based ABI that lets two libraries share columnar buffers without copying them. The CX side is libcx_arrow, a separate dynamic library that depends on libcx + the Arrow C-Data ABI. Core libcx is Arrow-free; capability bit 23 advertises Arrow when libcx_arrow is loaded.

    The bridge exports four C ABI symbols (spec/core/abi.md §2.11): cx_arrow_export_open / cx_arrow_export_open_fd for CXCol → Arrow, and cx_arrow_import_to_data_bin / cx_arrow_import_to_data_bin_fd for Arrow → CXCol. The Python binding wraps them as cxlib.arrow.export (framed CXCol bytes in, pyarrow.RecordBatchReader out) and cxlib.arrow.import_to_data_bin (the inverse).

    Zero-copy handoff

    The Arrow C Data Interface uses two structs: ArrowSchema (column types + names) and ArrowArray (per-batch buffers, including null bitmap, offsets, and values). CX populates these structs to point at its own column buffers; consumers (DuckDB, Polars, PyArrow, etc.) read from the same memory pages CX wrote.

    Ownership crosses the boundary explicitly. The exporter populates an ArrowArrayStream with a release callback; the consumer calls release when done. CX's release callback frees the underlying CXCol buffers. There is no GC interplay — bindings hold the Arrow stream as an opaque handle until they're done with it.

            import cxlib
           import cxlib.arrow as cxa

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())

           # Zero-copy export: pointer handoff over the C Data Interface
           reader = cxa.export(framed)       # pyarrow.RecordBatchReader
           pa_table = reader.read_all()      # pyarrow.Table

           # Symmetric inverse: Arrow → framed CXCol bytes
           framed_again = cxa.import_to_data_bin(pa_table)

    Go and Rust use the same four symbols through the C ABI with each host's Arrow FFI layer (arrow-go, the arrow crate's ffi_stream module) — the per-binding Arrow libraries are tabulated in spec/core/abi.md §2.11.

    Type mapping

    The CX ↔ Arrow type map is normative (spec/misc/type-mapping.md). The high-level summary:

    • int / i64 ↔ Int64; i32 ↔ Int32; sized variants (i8–u64) map to corresponding Arrow sized integer types.
    • float / f64 ↔ Float64; f32 ↔ Float32; f16 ↔ Float16.
    • bool ↔ Boolean (bit-packed in Arrow).
    • string ↔ Utf8 (or LargeUtf8 for columns whose total byte length exceeds 2 GB).
    • bytes ↔ Binary (or LargeBinary similarly).
    • date ↔ Date32 (days since 1970-01-01, proleptic Gregorian).
    • datetime ↔ Timestamp(Nanoseconds, UTC) (Arrow format string tsn:UTC).
    • decimal ↔ Decimal128 / Decimal256 by coefficient width.
    • Nullable columns → Arrow's standard nullable variant (validity bitmap).

    Current column-type coverage in libcx_arrow is all ten column types — int / i8 / i16 / i32 / float / bool / string / date / bytes / datetime (the last as timestamp[ns, UTC]). Deferred: decimal and dictionary-encoded columns — each surfaces a clear not yet supported error rather than a lossy fallback.

    Arrow IPC stream format

    Beyond zero-copy in-process handoff, CXCol can emit Arrow IPC streams for cross-process or cross-host transport. The IPC stream is Arrow's own serialization (schema header + record batches + EOF), distinct from the C Data Interface (in-memory structs).

            import cxlib
           import cxlib.arrow as cxa

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())

           ipc = cxa.to_ipc(framed)              # Arrow IPC stream bytes
           cxa.write_ipc_file(framed, 'orders.arrow')

           framed_back = cxa.from_ipc(ipc)       # inverse
           framed_back2 = cxa.read_ipc_file('orders.arrow')

    The cx table dump FILE --to=arrow [--output=FILE] CLI subcommand (spec/misc/cli.md) writes the IPC stream form.

    Arrow Flight (planned)

    Arrow Flight is Arrow's gRPC-based RPC framing for cross- process record batches. It is the natural next layer above the IPC stream — a Flight server publishes batches by descriptor; a Flight client subscribes. CX integration is planned: no Flight surface ships currently; the tooling-layer story will be specified when it lands.

    For cross-process CXCol transport currently, use Arrow IPC over your existing transport (HTTP, pipe, socket). The [?http-client] directive can carry Arrow IPC streams as binary bodies.

    Parquet bridge

    CXCol bridges to Apache Parquet via Arrow: CXCol → Arrow stream → Parquet file. Core libcx has no direct Parquet C++ dependency — adding one would couple every binding to a heavyweight build-time toolchain. The Parquet adapter lives at the binding layer, chained off the Arrow bridge; the Python binding ships the reference composition (cxlib.parquet, on pyarrow.parquet).

    Writing Parquet

    cxlib.parquet.write_table(cx_data_bin, path, …) walks framed CXCol bytes → Arrow record batches → the PyArrow Parquet writer. The Parquet writer is the host binding's choice; the CXCol side just provides the Arrow stream.

            import cxlib
           import cxlib.parquet as cxpq

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())
           cxpq.write_table(
               framed,
               'orders.parquet',
               compression='snappy',     # Parquet ecosystem default
               row_group_size=1_048_576, # match CXCol canonical chunk
           )

    Defaults are the Parquet-ecosystem defaults (Snappy, not zstd) — output is meant to be consumed by Parquet readers that assume Snappy. Zstd is CX's default for CXCol's 0x90 page compression; the two formats use their own ecosystem defaults to minimize friction with the consumers of each.

    spec/misc/table-api.md §3 declares the per-binding adapter slots (Rust via arrow-rs + the parquet crate, Go via arrow-go); those bindings reach Parquet through the Arrow C ABI today — the packaged one-call adapters have not shipped outside Python.

    Reading Parquet

    cxlib.parquet.read_table(path) is the symmetric inverse: the PyArrow Parquet reader produces Arrow record batches, and the bridge imports them as framed CXCol chunked-table bytes — ready for cxlib.from_data_bin or a streaming cxlib.TableReader pass.

            import cxlib
           import cxlib.parquet as cxpq

           framed = cxpq.read_table('orders.parquet')

           # Whole-value view
           print(cxlib.from_data_bin(framed))

           # Streaming view — one row group at a time
           with cxlib.TableReader(framed) as r:
               for group in r:
                   process(group)

    Column projection and predicate pushdown are the host Parquet reader's work, done before the batches reach CX: a Parquet reader given per-row-group statistics skips the groups a predicate rules out, so I/O saved is proportional to the row groups skipped. Files without statistics still read correctly — the reader degrades to a full scan.

    CX ↔ Parquet type mapping

    The mapping is normative. Most types round-trip cleanly through Arrow; a small number of CX types have lossy edges, and the bridge reports them loudly rather than silently coercing.

    • int / i64 → INT64.
    • i32 → INT32; i16 / i8 → INT32 with INT(N, true) logical type; unsigned similarly.
    • f64 / float → DOUBLE; f32 → FLOAT; f16 → FIXED_LEN_BYTE_ARRAY(2) / FLOAT16 (the latter is non-standard pre-Parquet 1.13).
    • bool → BOOLEAN.
    • string → BYTE_ARRAY with STRING logical type (UTF-8).
    • bytes → BYTE_ARRAY.
    • date → INT32 with DATE logical type.
    • datetime (UTC) → INT64 with TIMESTAMP(NANOS, isAdjustedToUTC=true).
    • decimal → DECIMAL(p, s) (Parquet caps at 256-bit precision).
    • Nullable columns → OPTIONAL repetition.

    Types outside the bridge's current coverage (see arrow-type-mapping) refuse with a clear error at the Arrow boundary rather than degrading — the same loud-never-lossy posture as the wire format itself.

    Round-trip identity

    CX → Parquet → CX is not in general byte-identical. Parquet is a presentation-layer format: footer offsets shift, row-group sizes are writer-dependent, encoding choices (dictionary thresholds, page sizes, compression codec) are per-writer. Many byte-level Parquet files encode the same logical data. CXCol fills this niche precisely — it is the hashable origin; Parquet is the bridge.

    Logical round-trip is normative: a CX table emitted as Parquet and re-imported produces the same [table[…]] block with the same column names, types, row count, and cell values (modulo the documented lossy edges in 5.5.3).

            import cxlib
           import cxlib.parquet as cxpq

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())
           cxpq.write_table(framed, 'orders.parquet')
           framed2 = cxpq.read_table('orders.parquet')

           # Logical equality holds across the round-trip
           assert cxlib.from_data_bin(framed) == cxlib.from_data_bin(framed2)

    Schema identity across the bridge

    Parquet output carries the data, not the CX schema reference. CX schema identity lives at the CXCol layer: a schema-driven file names its schema by content hash (the §3.13.1 reference forms), and the cx table subcommand resolves --schema-from= arguments to a content hash before emit (spec/core/data-bin.md §3.13.1). A Parquet round-trip re-enters CX as a self-describing table; re-attach the schema by validating or re-encoding schema-driven against the same schema hash.

    Streaming evaluator over columnar data

    The CX streaming evaluator (spec/core/streaming.md) operates over CXCol chunks one at a time. The normative throughput gate is ≥ 200 MB/s sustained per streaming shape (spec/core/code.md §11.4.4, gate 15). The gate is not green at this release: [?for] measures ~200 MB/s and [?map] 129.2 MB/s; closing the [?map] gap is tracked for the next cycle.

    The streaming evaluator emits three table-specific events when it encounters a CXCol input: StartTable (column spec), RowGroup (one chunk's data), EndTable (close). Directives that consume the stream see one row group at a time and never materialize the full table.

    Today the consumer surface for CXCol streams is the CLI and the Table API (cx table info / dump / load, and the host-language bindings' table methods):

          cx table info big.cxbin          [# column spec, row count, size #]
         cx table dump big.cxbin --to=cx  [# stream to CX text            #]

    The design direction (not yet shipped as CX-code surface): any directive that takes a CXPath iterator participates in a CXCol stream. [?for] / [?modify] / [?map] / [?reduce] (see code) all participate. Bounded memory is preserved end-to-end: a pipeline of N stages holds N row groups in flight, not N × row-count.

    Streaming events

    The event vocabulary (spec/core/streaming.md) extends the standard StartElement / Scalar / EndElement events with three table-specific variants.

    • StartTable — fields: name (string), col_spec (binary blob; the column schema in ast_bin form). Emitted in place of the StartElement that would otherwise wrap a [table[…]] body.
    • RowGroup — fields: row_count (u32), payload (binary blob; one row group's column buffers). One event per row group, in source order.
    • EndTable — fields: name (string). Closes the sequence in place of the corresponding EndElement.

    A non-chunked 0x60 (whole-table) input emits the existing StartElement / per-cell-Scalar / EndElement sequence unchanged. Only 0x63 chunked-CXCol inputs produce the new events. Streaming consumers that don't care about the distinction can flatten via a helper that re-emits each RowGroup as a sequence of StartElement / row / EndElement triples.

    Performance posture

    The gate protocol is fixed by spec/core/code.md §11.4.4: every measured streaming shape must sustain a mean ≥ 200 MB/s with no single trial below 80% of the mean, and must demonstrably stream (more than one output chunk, the implementation's own streaming predicate reporting true). Re-run with make bench-code-streaming.

    Current status, honestly stated: the gate is not green — [?for] measures ~200 MB/s and [?map] 129.2 MB/s. Closing the [?map] gap is tracked for the next cycle. On the write side, the ABI streaming writer compresses a row group only when its body exceeds 64 KiB and compression beats 0.85 of the original size (spec/core/abi.md §2.10).

    Ecosystem integrations

    The Arrow C Data Interface is the integration layer the analytical ecosystem standardized on. Once CX exposes Arrow, the rest of the stack lights up — DuckDB, Polars, DataFusion, pandas, Spark via Parquet — most with zero-copy handoff in process, the rest with one copy at the boundary.

    DuckDB

    DuckDB consumes Arrow tables registered on a connection — zero-copy from CXCol's column buffers into DuckDB's vectorized executor via the C Data Interface.

            import cxlib, duckdb
           import cxlib.arrow as cxa

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())
           orders = cxa.export(framed).read_all()   # pyarrow.Table
           con = duckdb.connect()

           # Register the Arrow table — zero-copy via the C Data Interface
           con.register('orders', orders)

           result = con.execute('''
               SELECT customer, SUM(amount) AS total
               FROM orders
               GROUP BY customer
               ORDER BY total DESC
           ''').fetchall()

    DuckDB's executor reads directly from CX's column buffers during the scan. The result set is materialized into DuckDB's own memory; cxa.import_to_data_bin(con.execute(…) .arrow()) brings a result back as framed CXCol bytes — the symmetric inverse.

    Polars

    Polars is Arrow-native at the buffer level. CX → Polars in Python goes through the same export call — zero-copy for the underlying buffers.

            import cxlib, polars as pl
           import cxlib.arrow as cxa

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())
           df = pl.from_arrow(cxa.export(framed).read_all())

           # Polars query
           result = df.lazy().filter(pl.col('amount') > 100).collect()

    In Rust, the same handoff runs over the C ABI — the cx_arrow_export_open stream feeds the arrow crate's ffi_stream reader, and Polars consumes the record batches from there. A packaged Rust convenience wrapper has not shipped.

    pandas

    pandas is not zero-copy at the buffer level — its column model uses NumPy arrays with type-system mismatches against Arrow (no nullable integers, no first-class strings without StringDtype). CX → pandas is one Arrow round-trip plus one pandas conversion; expect one full data copy at the boundary.

            import cxlib
           import cxlib.arrow as cxa

           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())

           # PyArrow → pandas; one copy at the pandas boundary
           df = cxa.export(framed).read_all().to_pandas()

    spec/misc/table-api.md §3 declares a to_pandas() adapter slot on the Table type; the Python binding has not implemented it yet — the explicit Arrow route above is the shipped path.

    For DataFrame-style work where zero-copy matters, prefer Polars over pandas. pandas remains supported because the Python data-science ecosystem assumes it, but the cross-boundary cost is real on large tables.

    DataFusion (planned)

    Apache DataFusion is a Rust query engine over Arrow. Its TableProvider trait accepts arbitrary Arrow record-batch sources, so CXCol is a natural fit: register a .cxbin file as a DataFusion table, run SQL or DataFrame queries against it with the same zero-copy guarantees as Polars.

    Status: planned — no packaged CX-side convenience layer ships. Adopters who need DataFusion today wire it manually: cx_arrow_export_open over the C ABI into the arrow crate's ffi_stream reader, and the resulting record batches into a DataFusion MemTable. The path works; it just lacks the convenience layer.

    Spark and cluster compute

    Spark reads / writes Parquet natively. CXCol's Parquet bridge (see parquet-bridge) is the integration path — emit .parquet from CX, point Spark at the directory, run PySpark / Spark SQL. For zero-copy in cluster contexts, Arrow Flight is the long-term path; status is planned per arrow-flight.

            import cxlib
           import cxlib.parquet as cxpq
           from pyspark.sql import SparkSession

           # CX table → Parquet (one-time conversion)
           framed = cxlib.to_data_bin_chunked(open('orders.cx').read())
           cxpq.write_table(framed, 'orders.parquet')

           # Spark reads the Parquet directly
           spark = SparkSession.builder.getOrCreate()
           df = spark.read.parquet('orders.parquet')
           df.groupBy('customer').sum('amount').show()

    The Parquet bridge is one-way at this layer — Spark's writes come back through cx table load output.parquet --to=cx. For round-trip workflows, keep the CXCol file as the canonical origin and treat Spark's outputs as derived artifacts.

    Performance characteristics

    The analytics lane's perf budgets and where they're measured. The spec fixes the gates; the bench targets re-measure them — numbers live where they are re-run, not in prose that goes stale.

    • Streaming throughput. Spec gate: mean ≥ 200 MB/s per streaming shape, no trial below 80% of the mean (spec/core/code.md §11.4.4, gate 15; bench: make bench-code-streaming). Current status: not green — [?for] ~200 MB/s, [?map] 129.2 MB/s measured; tracked for the next cycle.
    • Parquet write (default Snappy, 2²⁰ row-group). Measured via PyArrow's writer on the CXCol → Arrow → Parquet path; throughput is dominated by the Parquet codec, not the CXCol bridge. Adopters should profile against their chosen Parquet writer; no normative CX-side gate.
    • Arrow zero-copy handoff. O(metadata) per batch — the schema and per-column buffer pointers are populated, no buffer is copied. Time per export is independent of row count and proportional to column count.
    • Predicate pushdown reduction. When the Parquet writer emitted per-row-group statistics, the host Parquet reader skips the row groups a predicate rules out — I/O saved is proportional to the groups skipped. Files without statistics degrade to a full scan.
    • Memory budget per stream stage. One row group in flight. The streaming evaluator (spec/core/streaming.md) is bounded by max(row_group_byte_size) regardless of table size.

    The 200 MB/s gate is for the streaming evaluator, not the raw CXCol reader — the reader has no evaluator pipeline in front of it, but its throughput is not separately gated or published. Per-binding adapter throughput varies by host — pandas is the slowest because of the boundary copy.

    When to use CXCol vs Parquet vs Arrow vs JSON

    Pick by use case. The four formats overlap in the analytics lane but each has a niche the others fill badly.

    • CXCol — use when CX content-addressable identity matters (caching, dedup, signing, provenance) or when you want streaming with the CX type system end to end. Single-writer, sequential-decode, hashable. Single-file format; not designed for query (use the Arrow bridge into DuckDB / Polars / DataFusion for that).
    • Parquet — use for cross-ecosystem interop (Spark, BigQuery, Snowflake, Trino, Athena, all the Hadoop- lineage tools). Carries the data, not CX's schema identity or metadata (see parquet-metadata). Not hashable in the byte-stable sense — different writers produce different bytes for the same logical data.
    • Arrow IPC stream — use for in-process or LAN-local zero-copy between CX and another Arrow-native consumer (DuckDB, Polars, DataFusion, pandas via PyArrow). No compression by default (Arrow is layout-oriented, not compression-oriented); not designed for long-term storage.
    • JSON / JSONL — use for ad-hoc human-readable interop or when the consumer truly is JSON-shaped. Lossy on type metadata (no distinction between int and float kinds, date-times become strings, dictionary encoding gone). The CX → JSON projection (see [[surfaces#json]]) handles the shape conversion; for tabular data specifically, JSONL (one row per line) is the conventional wire form.

    The decision tree, compressed:

    • Need a hashable, content-addressable origin? → CXCol.
    • Sharing with Spark / Snowflake / BigQuery / other non-Arrow-native tools? → Parquet.
    • In-process handoff to DuckDB / Polars / DataFusion / pandas? → Arrow (with CXCol as the origin).
    • Debugging, ad-hoc inspection, or a JSON-shaped consumer? → JSON / JSONL.

    In practice the layering is: CXCol as canonical origin → Arrow as the in-process bridge → Parquet for cross-ecosystem export. JSON is the human-readable view. The same logical table can move through all four; identity stays at CXCol.
