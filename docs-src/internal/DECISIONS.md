# v0.7.0 Doc-Gen Decisions Log

A running record of design and authoring decisions for the
documentation generator and the docs themselves. Append-only;
the most recent decision lives at the bottom. Each entry has a
date, the decision, and the rationale or context behind it.

Pair with [`V0_7_0_DOCS_DESIGN.md`](V0_7_0_DOCS_DESIGN.md) (the
overall design spec) and the inline notes in
[`../../scripts/gen_docs/build.cxl`](../../scripts/gen_docs/build.cxl).

## 2026-05-20 — Doc tree under `docs-src/`

The single source of truth for documentation content is
`docs-src/content/`. The build pipeline (`scripts/gen_docs/`)
renders that tree into `_docs_staging/` (markdown) and
`_site_staging/` (HTML); `make docs-publish` promotes staging to
the live `docs/` and `_site/` directories.

The previous hand-written `docs/*.md` files are archived under
`docs/archive/`. They remain as raw material for content ports
but are not regenerated by the scaffold.

---

## 2026-05-20 — Page schema fixed: `[page]` with `[section title=...]`

Every content page is a `[page id=...]` element whose meta block
declares title, layout, nav-order, audience, and summary. Body
elements available inside `[section]`:

- `[prose ...]` — narrative paragraph
- `[code lang=... src=...]` — fenced code block
- `[example-ref id=... show=...]` — pulls an example fixture
- `[list [item path=... label=...]]` — bulleted nav-link list
- `[table-md src='''markdown table''']` — full markdown table
  (post-processed into `<table>` for HTML)
- `[cx-playground]` — placeholder; substituted by post_html
- `[preserve id=...]` — survives regeneration

Sections render with `<h2>` from `@title` (preferred) or `@id`
(fallback). Slug IDs stay as anchor targets; titles are the
display form.

## 2026-05-20 — Sidebar derives from `site.cx`

`scaffold.sh build_nav` extracts `[group label='...']` and
`[item path='...' label='...']` entries from `site.cx` and emits
an `<aside class="sidebar">` with section headings and a flat
link list per group. Active page is highlighted blue. Brand
"CX" links to `/index.html`; a "GitHub →" sub-link goes to
`github.com/cx-home/cx`.

The sidebar is injected on every page by `post_html`. Adding a
new page requires only adding a `[item ...]` entry to `site.cx`
and writing the corresponding `docs-src/content/<path>.cx` file.

## 2026-05-20 — Root-relative HTML hrefs (superseded)

Originally rewrote every internal link to root-relative
(`href="/install.html"`). Worked under any HTTP server with the
doc root at `/` but broke under `file://` — `/install.html`
resolves to the filesystem root, not the doc root. Superseded
by the depth-prefix scheme below.

## 2026-05-20 — Depth-relative hrefs (current)

Internal links are emitted as relative paths walked back to the
doc root via `../` segments. `scaffold.sh depth_prefix($rel)`
counts the slashes in the page path to compute the prefix:
`index` → `""`; `bindings/python` → `"../"`;
`a/b/c/page` → `"../../../"`. Every `href="<path>"` becomes
`href="<prefix><path>.html"`; markdown counterpart prepends the
same prefix and appends `.md`.

This works for both `file://` (no web server) and any HTTP server
pointed at the doc root. Verified: `index.html` → `install.html`
(no prefix), `bindings/python.html` → `../install.html`,
brand link from any depth points back to `index.html` via the
right number of `../`.

Playground asset paths (`/playground/playground.js`, `.css`) are
rewritten the same way inside the cx-playground HTML snippet
before substitution.

## 2026-05-20 — Tables via `[table-md]` + awk post-process

Markdown tables in source live in a `[table-md src='''...''']`
element. The same source serves both targets:

- For Markdown: cx --md emits the multi-line paragraph
  verbatim; GitHub renders as a table.
- For HTML: `post_html` awk pass detects the markdown-table
  pattern inside a `<p>` (pipe-delimited rows with a separator
  row) and rewrites to `<thead>`/`<tbody>` markup with proper
  styling from `style.css`.

Considered and rejected: extending `[table]` schema with
`[row]` children (more verbose authoring); cx --xml native
table emit (does not exist).

## 2026-05-20 — Playground integration via `<cx-playground/>` marker

The Playground page contains a single `[cx-playground]` element
in its body. `cx --xml` emits `<cx-playground/>`. `post_html`
detects the marker and substitutes the full Playground HTML
snippet plus a `<script>` and `<link>` for the JS and CSS bundle.

Assets live at `scripts/gen_docs/playground/{playground.html,
playground.js,playground.css}`. The JS ships a static-corpus
sandbox with 8 starter examples and three projection tabs
(canonical, JSON, XML). A live libcx-WASM evaluator is on the
v0.7.x roadmap.

## 2026-05-20 — Parser hazards we work around in authoring

The CX parser has several sharp edges that bite when authoring
prose inside `[prose ...]` and `[code src=...]` bodies. The
workarounds below are part of the doc-gen authoring contract.

| Hazard | Workaround |
|---|---|
| `[?cx include]` directive at top-level of authored prose | Reference the directive by name in prose; show in a `[code lang='cx']` block |
| Embedded triple-quoted strings inside double-quoted `src="..."` | Split into two `[code lang='cx' src='...']` blocks |
| Markdown-style three-dash separator inside any string | Replace with prose describing the separator |
| `[- ... ]` block comments containing `[#` / `[|` inside | Keep block comments prose-like; no embedded CX-shaped syntax |
| `:table[...]` inside bare prose | Reword to "the colon-table form" |
| `[ref @id]` inside bare prose | Reword; do not write `@id` references in prose |
| `[?if [...]]` shape inside bare prose | Show in a `[code]` block, not in prose |
| Mid-content `&` mid-word (e.g. `Identity & canonical`) | Use `and` or em-dash in link labels and prose |

Fixes that have landed at parser/evaluator level so we do *not*
need to work around them: mid-word apostrophes (`it's broken`,
commit `5f207359`); newlines / brackets / quotes in substituted
attribute values (commit `3b7f51b5`); `#` in substituted values
(commit `17cf46de`); `&` in substituted values; SequenceNode in
`element_text_content` (commit `ca66ac10`).

## 2026-05-20 — Title case for section headings

Every `[section]` carries an explicit `title='...'` attribute in
Title Case. Acronyms keep their case (`CLI`, `CXL`, `JSON`,
`YAML`, `TOML`, `XML`, `LSP`, `ast-bin`, `data-bin`). Slug
`id='...'` stays lowercase-kebab for anchor targets.

Rejected: lowercase headings (felt unfinished); ALL-CAPS
section IDs; sentence-case (inconsistent in a reference doc).

## 2026-05-20 — Per-language Bindings pages

Each binding gets its own page under `bindings/<language>.cx`
with install, parse/emit, eval, validate, streaming, type
mapping, and binding-specific notes. The shared catalog at
`bindings/index.cx` lists every binding plus parity tiers; the
C ABI lives at `bindings/c-abi.cx` as the layer every binding
wraps.

Rejected: a single "Bindings" reference page with sections per
language (too long; the per-language pages let users land
directly via search).

## 2026-05-20 — Link discipline

Every internal href must resolve. The audit pass at the end of
the doc-gen turn runs:

```sh
grep -rohE 'href="/[^"]*\.html"' _site_staging/ \
  | sed 's|href="/||;s|"$||' | sort -u \
  | while read href; do
      [ -f "_site_staging/$href" ] || echo "BROKEN: $href"
    done
```

Target: zero broken internal links per render. Anything that
shows up gets fixed before commit.

External links (`http://`, `https://`, `mailto:`) are exempt
from the audit; they are linted by `make docs-check` (stub at
v0.7.0; full implementation in v0.7.x).
