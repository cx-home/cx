About CX

CX is one language for data and code. The same brackets that hold a configuration file hold a query, a transform, and the program that emits the report — one shape, one parser, one canonical form. This page is the story of why it exists.

The problem

A typical system speaks half a dozen serialization dialects at once: JSON on the wire, YAML for configuration, TOML for a tool here and there, XML for documents, CSV for tables, plus a templating language to produce output and a query language to pick things out of it. Every boundary between them is a lossy conversion and a place for bugs to hide. Comments vanish. Types soften. The same value hashes differently depending on which tool last touched it. None of these formats can describe both the data and the computation over the data, so every project re-invents a glue layer.

The idea

CX collapses that stack into a single bracketed surface. Everything is a [head …] form: an element, a directive, a call, a value. Data is a program that evaluates to itself, so the same syntax that holds your configuration also expresses the query (CXPath), the pattern match ([?match]), and the transform ([?modify]) over it. Conversions to and from JSON, YAML, TOML, and XML are defined to round-trip without semantic loss, and every document has a stable identity: the SHA-256 of its canonical bytes, unchanged by whitespace, comments, or attribute order.

The design follows a few rules that show up everywhere in the language: one shape for everything; every construct reads left-to-right; nothing is lost in a round-trip that doesn't have to be; and the canonical form is the source of identity. The rest of this guide is the working-out of those rules.
