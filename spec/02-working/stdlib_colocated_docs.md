# Co-located stdlib documentation (CX-native, self-sourcing)

**Status:** 02-inprogress (DRAFT — not graduated; only the user moves this to 03-approved)

**Target version:** v0.8.0

## §0. Goal

The bundle stdlib modules under `/stdlib/<m>.cx` are the **single source of
truth** for the standard library's documentation. Each public function's
contract prose and worked examples live **co-located** with its `[?def]`, in
CX. Examples double as conformance fixtures (write-once: documents AND tests).

The spec markdown (`spec/std-lib/<m>.md`), the guide's §16 "Standard library"
section, and the coverage report are all **derived views**, generated by one
CX program walking the bundle, and gated so they cannot drift.

This document defines the **co-located doc schema** — the CX shape doc/example
metadata takes inside each module file.

## §1. Why sibling blocks (not `[?def]` body children)

A natural idea is to nest `[doc]`/`[example]` *inside* each `[?def]` body
(eval ignores non-final body expressions, so they are inert at runtime).
However, the **data codec stringifies `[?…]` directives**: `[$cx:parse]` of a
`[?def …]` form returns a single opaque string, not a navigable element tree
(this is deliberate — it is what lets the codec round-trip directives
losslessly). A CX projection therefore **cannot** reach doc/example children
that live inside a `[?def]`.

Plain (non-directive) elements *do* parse into a navigable tree. So the doc
metadata is carried in **sibling plain elements** placed immediately after each
`[?def]`, and a **module-level** plain element for the scope prose. The module
loader ignores any top-level form that is not `[?lib]`/`[?def]`/`[?const]`
(`module_loader_scan_directives` skips non-directives), so these blocks are
inert at load time and add **no language change**.

## §2. Schema

### §2.1 Module scope block — once per module, at the top

```cx
[module-doc name=<module>
  [scope """<the §1 Scope prose for this module — one or more paragraphs>"""]]
```

- `name` (attr, required): the bare module name, e.g. `path`, `strings`.
- `[scope """…"""]` (child, required): the module's scope/overview prose. Use a
  triple-quoted (raw) string so prose may contain any punctuation verbatim.

### §2.2 Per-function block — one per public `[?def]`, placed right after it

```cx
[?def dirname scope=public pure [returns string] ($p::string) [$path-dirname $p]]
[fn-doc name=dirname scope=public purity=pure
  [sig """($p::string) -> string"""]
  [summary """Return the directory portion of a path — everything up to (but not
              including) the final separator."""]
  [example [code """[$path:dirname "/usr/local/bin"]"""] [expect """/usr/local"""]]]
```

- `name` (attr, required): the function name; MUST match the sibling `[?def]`.
- `scope` (attr, required): mirrors the def's `scope=` (`public` / `internal`).
- `purity` (attr, required): `pure` or `impure`; mirrors the def's purity token.
- `[sig """…"""]` (child, required): the human-readable signature, raw string so
  `::`/parens/`*` appear verbatim. Convention: `(<args>) -> <return-type>`.
- `[summary """…"""]` (child, required): one- to few-sentence description.
- `[example …]` (child, zero or more): a worked example. Each carries:
  - `[code """<cx source>"""]` — the example program (raw string, verbatim CX).
  - `[expect """<canonical output>"""]` — the exact expected output of running
    `code` through the `cx` evaluator.

  Examples SHOULD be present for every public function; in Phase 2 they become
  the module's conformance fixtures (the `code`/`expect` pair is run as a test).

### §2.3 Authoring rules

- All structured fields are **attributes** or **plain-element children** so the
  block round-trips through `[$cx:parse]`. Do not place a positional bareword
  (like the function name) before the attributes — a bareword in content
  position followed by `k=v` tokens collapses the whole run into text.
- `[fn-doc]` blocks restate `scope`/`purity`/`sig`. The `[?def]` remains the
  runtime source of truth; a **freshness gate** asserts each `[fn-doc]` agrees
  with its `[?def]` (presence parity + signature/scope/purity match), so the
  restatement cannot silently drift (see §4).

## §3. Derived views (consumers)

One CX projection program (`scripts/gen_*`, Phase 4) walks every
`/stdlib/<m>.cx`, reads `[module-doc]` + `[fn-doc]` via `[$cx:parse]` + CXPath,
and emits:

1. **Coverage data** — replaces `conformance/stdlib/coverage.cx`; nested
   (per-module → per-function), not the legacy flat shape.
2. **Guide §16** — `docs-src/canonical/sections/16-libraries.cxd`, covering ALL
   bundled modules.
3. **Spec mirror** — `spec/std-lib/<m>.md`, regenerated from the bundle.

## §4. Gates (Phase 5)

- **Presence parity:** every public `[?def NAME]` has a matching `[fn-doc
  name=NAME]` and vice-versa.
- **Signature freshness:** each `[fn-doc]`'s `scope`/`purity`/`sig` agrees with
  its `[?def]`.
- **Examples as fixtures:** every `[example]`'s `code`→`expect` runs green
  through conformance.
- **Derived-view freshness:** regenerate coverage + §16 + spec mirror and assert
  unchanged in CI; a deliberately-stale artifact fails.

## §5. Non-goals / open

- No change to the `[?def]` grammar or to eval. The doc blocks are pure data.
- Whether `[fn-doc]` should eventually be folded into the codec as structured
  program introspection (so `sig`/`scope`/`purity` need not be restated) is left
  open; the freshness gate makes the restatement safe in the interim.
