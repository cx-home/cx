# CX Internationalization Specification
# Version: 1.0
# Date: 2026-05-07

This document specifies CX's normative i18n behavior: language
tagging via the `cx:lang` attribute, character-encoding policy,
Unicode normalization, bidirectional text handling, and the
relationship between CX's i18n primitives and equivalents in XML
and other source formats.

Most of CX's i18n posture is established by other specs and
referenced here for completeness:

- **UTF-8 encoding** is mandatory — see `spec/abi.md §1.7`.
- **Unicode normalization** is *not* applied on storage or
 canonical output — see `spec/policies.md §2.5`.
- **BOM handling** silently strips a leading UTF-8 BOM and never
 emits one — see `spec/policies.md §2.3`.
- **Locale independence** for numeric/date formatting — see
 `spec/abi.md §1.6`.
- **Identifier rules** are Unicode-correct per the grammar's
 `NameStartChar` / `NameChar` productions — see
 `spec/grammar.ebnf §Identifier`.

The genuinely new content in this document is:

- `cx:lang` attribute and inheritance semantics (§1).
- `xml:lang` import-alias behavior (§2).
- Bidirectional text rule (§3).

---

## 1 — `cx:lang` attribute

### 1.1 Syntax

`cx:lang` is a reserved attribute name carrying a BCP 47 language
tag. It may appear on any element:

```cx
[para cx:lang=en
 Hello, world.
]

[content cx:lang=zh-Hans
 [title 你好世界]
 [body 这是中文内容]
]

[mixed cx:lang=en
 [quote cx:lang=fr Bonjour le monde]
 English narration around a French quote.
]
```

The attribute value must be a syntactically valid BCP 47
language tag (RFC 5646). The parser does not validate the tag
against the IANA registry — well-formed-but-unregistered tags
parse without error. Common forms:

- Plain language: `en`, `fr`, `zh`, `ar`
- Language + script: `zh-Hans`, `zh-Hant`, `sr-Cyrl`, `sr-Latn`
- Language + region: `en-US`, `en-GB`, `pt-BR`, `pt-PT`
- Language + script + region: `zh-Hans-CN`, `zh-Hant-TW`
- Language + variant: `de-1996`, `sl-rozaj`
- Private-use: `x-klingon`, `en-x-internal-tag`

### 1.2 Reserved-prefix consistency

The `cx:` prefix is reserved §D4.
`cx:lang` is part of that reservation; adopters cannot redeclare
`cx:` to a different namespace and use `cx:lang` for unrelated
data.

### 1.3 Inherited scope

`cx:lang` is **inherited** through descendant elements until
redeclared. The element bearing `cx:lang` plus all of its
descendants are tagged with that language unless a descendant
declares its own `cx:lang`. This matches XML's `xml:lang`
semantics (W3C XML 1.0 §2.12).

```cx
[doc cx:lang=en
 [title English title]
 [body English body
 [aside cx:lang=fr
 [span French content]
 [nested
 [deep Still French]
 ]
 ]
 [back-to-english Back to English]
 ]
]
```

The inherited-language stack is part of the parsed AST. Bindings
expose it via `node.lang` (or per-language idiomatic spelling),
which returns the resolved language tag at that node — either
the locally-declared tag or the nearest ancestor's tag, or null
if no `cx:lang` is in scope.

### 1.4 Empty value

`cx:lang=""` (explicit empty string) means "no language declared
for this subtree" — it shadows an ancestor's `cx:lang` without
substituting a different tag. This matches XML's `xml:lang=""`
semantics.

### 1.5 Conversion behavior

| direction | behavior |
| --------- | -------- |
| CX → XML | `cx:lang` emits as `xml:lang` (the standard XML attribute, namespace `http://www.w3.org/XML/1998/namespace`). |
| CX → JSON / YAML / TOML | `cx:lang` emits as a literal `"cx:lang": "<tag>"` field on the resulting object. Adopters who need a different shape use the still-pending output-shape control mechanism (ROADMAP "Next > Conversion shape control"). |
| CX → Markdown | `cx:lang` is stripped (Markdown has no language-tag concept). Loss is documented per the precedent of . |
| CX → CSV / TSV / PSV | `cx:lang` becomes a `cx:lang` column when shape detection produces one (per); otherwise stripped. |
| XML → CX | `xml:lang` imports as `cx:lang` (see §2 below). |
| JSON / YAML / TOML / MD → CX | No language information is inferred; imported CX has no `cx:lang` declarations. |

### 1.6 Equality and canonical form

`cx_eq` compares `cx:lang` values bit-exactly (no case folding,
no tag-canonicalization). Two documents differing only in
`cx:lang=en-US` vs `cx:lang=en-us` compare unequal — BCP 47
case is conventionally lowercase-language / titlecase-script /
uppercase-region but is not normatively case-insensitive in CX.

Consumers who need case-insensitive language matching apply
their own folding before comparison.

`cx canonical` preserves `cx:lang` values exactly. The strict
canonical form does not normalize tag case.

## 2 — `xml:lang` import alias

When CX parses an XML document containing `xml:lang`, the
attribute is imported as `cx:lang` on the resulting CX
element. This makes XML round-trip lossless for the language
dimension:

```
XML in: <para xml:lang="en">Hello</para>
CX text: [para cx:lang=en Hello]
XML out: <para xml:lang="en">Hello</para>
```

The reverse direction also holds: `cx:lang` on a CX element
emits as `xml:lang` (in the XML namespace) on XML output. Per
 §D4, `xml:lang` resolves
to the standard XML namespace (`http://www.w3.org/XML/1998/namespace`)
and is recognized whether or not the user declared `xmlns:xml=...`.

This alias-on-import / canonical-on-export pattern means a CX
document is the canonical representation; XML documents in the
ecosystem may legitimately use `xml:lang`, but inside CX the
attribute name is always `cx:lang`. Bindings read `cx:lang` only;
they do not need to look at `xml:lang`.

## 3 — Bidirectional text

CX is a data/document format, not a rendering format. Its bidi
posture:

- **Storage**: CX stores text byte-exactly. Bidi-relevant
 characters (Unicode bidi control codepoints U+202A–U+202E,
 U+2066–U+2069, isolate / embedding / override marks) are
 preserved through parse, canonical-form, hash, and emit
 without modification.
- **Rendering**: bidi rendering is the consumer's responsibility.
 A consumer applying CX content to a UI applies the Unicode
 Bidirectional Algorithm (UAX #9) on its own.
- **No CX directional attribute**: CX does not provide an HTML-
 style `dir="ltr"` / `dir="rtl"` attribute. The reasoning is
 the same as `xml:space`: the format models data, not
 presentation.

For CX → XML conversion, an XML emitter that needs `dir` on a
specific element to produce well-formed XML for HTML-derived
schemas adds it post-conversion. CX itself does not generate
or consume `dir`.

## 4 — Conformance

A binding is i18n-conformant iff:

1. UTF-8-only input/output per `spec/abi.md §1.7`. Invalid UTF-8
 on any input boundary is rejected per `spec/policies.md §2.1`.
2. BOM handling per `spec/policies.md §2.3`.
3. Unicode normalization per `spec/policies.md §2.5`.
4. `cx:lang` round-trips bit-exactly through the binding's
 parse + emit path.
5. `node.lang` (or idiomatic spelling) returns the resolved
 inherited language tag at any node, or null if no `cx:lang`
 is in scope.
6. XML conversion preserves the `xml:lang` ↔ `cx:lang`
 round-trip per §2.

Conformance fixtures are under `vcx/tests/conformance/i18n/`
(to be added during the v0.6.0 implementation cycle).

## 5 — Open questions deferred to post-v0.6.0

These are not blockers for v0.6.0 but are tracked here for
visibility:

- **Tag canonicalization**. BCP 47 §4.4 defines a canonical-case
 rule (lowercase language, titlecase script, uppercase region).
 CX could optionally normalize on parse. Post-v0.6.0 if
 adopters surface a need.
- **Tag validation against the IANA registry**. Today's parser
 accepts any well-formed tag; a stricter mode could reject
 unregistered subtags. Post-v0.6.0 if useful.
- **Locale-aware comparison**. `cx_eq` compares language tags
 byte-exactly. A locale-sensitive comparison primitive could
 be added as a separate function (`cx_lang_match`). Not in
 scope for v0.6.0.
