## 1394-a — the deployment surface is a stdlib module of MOUNTABLE HANDLERS plus ONE graded in-tree deployment; the pending request lives in the session store seam

### The fork

- **(a) `cx-stdlib/sso`: a stdlib module of handler verbs a deployment MOUNTS, and one graded reference deployment that mounts them.** The module exports request→response verbs in the §10.3.3 shapes — an OIDC `login` (begin + park the request + 302), the OIDC `callback` (take the parked request by `state`, `complete`, establish the session, 302 to the parked return-to), the SAML `acs` (form body → `SAMLResponse` base64 → `attach-saml` → `RelayState` 302), the SAML `metadata` (#1402a), the `logout` pair, and the SCIM route set behind a bearer `[auth]`. A deployment mounts them as `[resource]` handlers on its own `[?http-service]`, or on the XAP host's route surface (#1292 is that item). One in-tree deployment program mounts every one of them and is graded by the S2 interop lane, two processes. DELETES nothing that exists. It ADDS one module and one program.
- **(b) a `cx sso serve` CLI subcommand.** DELETES dogfood — the deployment's logic moves into the CLI (V, or a CX program the binary embeds) where a customer cannot read, mount or modify it — and it forces a SECOND process on a SECOND port beside the product's own listener, which is a cookie-domain and reverse-proxy problem on day one in a corporate network. A customer whose XAP already serves cannot mount the callback into that listener. Wrong.
- **(c) part of the XAP host (`$xap:serve` grows a `[login]` block).** DELETES the separation `xap.md` §22.1 and `session.md` §2.2 draw — the host's wire auth is XSP-AUTH and the IdP is "integrated, never built" — and ties enterprise login to XAP, so a plain `[?http-service]` product has no login at all. It also puts three protocols' worth of HTTP in the host that #1393 just finished making honest. Wrong, and the reason it is tempting (the products are XAPs) is served by (a)'s XAP-mount rider.

**Ruled (a).** The long-term-best reason: every serving surface in the tree already speaks one request/response shape (`code.md` §10.3.3 is normative), so a handler verb is the one artifact that works on all of them, and a module of verbs is the only shape that lets the graded deployment and the customer's real deployment be THE SAME CODE. That is what "no surprises in a client's SSO environment" needs: the thing we tested is the thing they run.

### Riders, all load-bearing

1. **The pending authorization request lives in the session module's store seam (#1395), not in a session.** `oidc.md:47` ("persist `$req` in the session") cannot be followed: no session exists pre-login, and a guest session needs an anonymous-floor policy not every deployment admits. Ruled: `session` gains a **pending-request table** in the same store the sessions will live in (#1395's `cfg.store` URL — one backend, one configuration key), keyed by `state`, **single-use** (the take deletes), **TTL-bounded** (`pending-ttl`, default 10 minutes — the authorization-code lifetime OAuth 2.1 §4.1.2 bounds at 10 minutes). The SAML `AuthnRequest` id (#1402b) parks in the same table. Spec text to change: `oidc.md` §2.1 sentence at :47 names the pending store; `session.md` §3.1 gains `store` and `pending-ttl`. **Flagged: spec text changes, delegated G3.**
2. **N-SESSION-1 holds.** The callback handler does not hand session a claim set it did not verify: `session` gains `attach-oidc`, the SIXTH attach path, which runs `oidc:complete` in-path exactly as `attach-saml` runs the saml pipeline in-path, wrapping an oidc fault as `CXER4801` with the `CXER53xx` in `[cause]`. "There is deliberately NO verb that attaches a claim set it did not verify" stays true.
3. **Form bodies.** The ACS handler parses `application/x-www-form-urlencoded` with `url:query-parse` — the body IS a query string, and `oidc.md:149`'s "CX already has one query parser" argument applies unchanged. No second parser.
4. **The SCIM route set stays a MOUNT of the `scim` module**, which stays a semantics module (RULED C-1 untouched). The bearer check is a `[resource]` `[auth]` guard the module supplies, comparing against a configured token in constant time.
5. **Order.** S6 (#1395) lands the store seam + pending table; S7 (#1394) lands the module and the deployment. The S2 interop lane grades the stdlib verbs against the CX IdP server BEFORE S7 exists and the deployment AFTER; S2 does not wait on this ruling's implementation.

## 1397-a — `attach-saml` is STRICT, with no opt-out; the pure verbs keep the opts-gated rule via a `strict` opt that `attach-saml` always sets

### The fork

- **(a) strict by default on the login surface, no opt-out; the pure verbs are unchanged unless `opts.strict` is set.** `session:attach-saml` refuses to run the pipeline unless `cfg.saml` names `issuer`, `audience`, `recipient` and `now`, and either `in-response-to` or an explicit `idp-initiated: true`; it always passes `strict: true` to `validate`/`assertion`, under which an assertion with no `Conditions/@NotOnOrAfter`, a bearer `SubjectConfirmation` with no `SubjectConfirmationData`, or a `SubjectConfirmationData` carrying no `Recipient` is refused, and a supplied option that the document's signature placement cannot honour is refused rather than ignored. DELETES: the ability to mint a session from an under-configured `cfg.saml` — which is the defect. The shipped example `examples/platform/sso/saml-assertion-session/session.cx:33-36` is that deployment and must gain the keys (it is IdP-initiated: `idp-initiated: true`).
- **(b) strict as an opt-IN (`cfg.saml.strict: true`), lenient default.** DELETES nothing today and therefore fixes nothing: the shipped example stays green as written, and the next deployment copied from it is the misconfigured-but-green login this issue measured. A security default nobody turns on is not a default.
- **(c) strict by default with a `strict: false` opt-out.** The opt-out IS the fail-open knob, on a product surface, one line from an operator under time pressure during an outage. The pure verbs already exist for a caller that wants lenient composition; a login has no honest use for lenient. Refused.

**Ruled (a).** Placement, so the layers stay honest: the CONFIG-completeness refusal is session's — new code **`CXER4813 E_SESSION_ATTACH_UNDERSPECIFIED`** (the caller's fault; not a token rejection, so NOT wrapped as 4801), naming every missing key at once. The DOCUMENT-shape refusals are saml's under `opts.strict` — `CXER5406` for the missing `NotOnOrAfter`, `CXER5407` for the missing `SubjectConfirmationData`/`Recipient`, `CXER5408` for an option the placement cannot honour — and reach the caller wrapped as `CXER4801` with the `CXER54xx` in `[cause]`, exactly as today's refusals do.

### The envelope in the signed-Assertion-only shape, decided key by key

- `issuer` — the Assertion's `Issuer` is signed and IS checked (`:691-696`); the unsigned Response `Issuer` stays unread. Honourable in every shape. Required.
- `audience` — signed, checked. Required.
- `recipient` — lives in the signed `SubjectConfirmationData`. Honourable in every shape. Required (every deployment knows its ACS URL).
- `in-response-to` — lives in the signed `SubjectConfirmationData` (and, unsigned, on the Response). Honourable in every shape via the confirmation data. Required unless `idp-initiated: true`; with `idp-initiated: true` a document whose `SubjectConfirmationData` carries an `InResponseTo` is refused (`CXER5407`) — an unsolicited response must not answer a request.
- `destination` — exists ONLY on the Response. Unsigned Response ⇒ **cannot be honoured** ⇒ under `strict` a supplied `destination` is refused with `CXER5408` naming the placement ("`destination` was supplied but the Response is unsigned; have the IdP sign the Response, or drop the key knowingly"). Not required, because most IdPs sign the Assertion only. Documented in `session.md` §3.1 together with `leeway` (both are read today and documented nowhere — measured on the issue).
- `Status` — unsigned data on an unsigned Response; stays unread (the standing reading in `saml.md` §4.2's closing sentence). Refusing on unsigned bytes is theatre; the memory `reference_flow_act_and_saml_status_traps` item 4 already records this as not-a-defect.

`@Version`, `SessionNotOnOrAfter` and the rest of the unread elements are 1404-a below. `NotOnOrAfter` becoming mandatory under strict makes `claims` always carry `exp` on the login path, so session's own expiry logic always has its input. Spec text to change: `saml.md` §2.3 (the `strict` opt and what it requires), §4.4/§4.5 arms; `session.md` §2.2 (strict, no opt-out), §3.1 (`destination`, `leeway`, `idp-initiated`), §8 (`CXER4813`). **Flagged: spec text changes, delegated G3.**

Conformance: one arm per refusal, ALL in the signed-Assertion-only shape (the corpus today has zero such arms — every envelope case signs the Response), plus a positive arm proving the fully-configured login still mints.

## 1399-a — `refresh` revalidates per OIDC Core §12.2 against the ORIGINAL claims; `authorize-url` and `begin` read `$opts` as extras; `audience` is emitted

### 1. What "revalidate" means when the nonce is gone

- **(a) `refresh` takes the original `[claims]` as `opts.previous` and runs §12.2: the returned ID token is validated by §5 with the nonce rule REPLACED by §12.2's ("SHOULD NOT be present; if present, MUST equal the original nonce") and with continuity checks added (`sub`, `aud`, `azp` equal to the original; `auth_time`, when present, equal to the original).** The nonce is NOT gone: it is a claim on the original `[claims]`, which is precisely what a session holds. Without `opts.previous` the checks that need the original are skipped and the nonce check is skipped, since there is no request to bind to (a refresh has none); signature, `iss`, `aud`/`azp`, `exp`, `iat` and `at_hash` still run. DELETES: `[no-claims]` on a refreshed value that DID carry an ID token — `claims` now works on it. Keeps `[no-claims]` when the provider returned no ID token, with the diagnostic saying that.
- **(b) require `opts.previous`.** Refuses the one honest use of `refresh` without it — a machine-ish caller holding only the refresh token — for no security gain: the checks it enables are continuity checks, and a token that passes signature/iss/aud/exp without them is still a valid token of that provider for that client. Safer-looking, worse.
- **(c) leave `refresh` as is and correct `oidc.md:130` to say the ID token is discarded.** Trues the spec down to the shortfall — refused on the standing rule — and leaves a refreshed session unable to read its principal. Wrong.

**Ruled 1(a).** Entra returns the original nonce on a refreshed ID token, which is why "if present MUST equal the original" has to be checkable and why (a) has to carry the original claims rather than skip.

### 2. `authorize-url` extras and `begin`'s opts

**Ruled (a): `authorize-url $config $request $opts` emits `$opts` as caller extras in input order, after the fixed set, exactly as §4 already says; `begin $config $opts` passes its `$opts` through to the URL it returns AND records them on the `[auth-request]` as an `[extras …]` child in input order, so `authorize-url $config $request` re-derives the byte-identical URL from the request alone.** An extra naming one of the eight fixed parameters (`response_type` … `code_challenge_method`) or a config-derived one is `CXER5310` — overriding `state` or `nonce` through extras is the hazard §2.1 exists to prevent. `domain_hint` (Entra) is the named consumer.

### 3. `audience` and `login-hint`

**Ruled: `audience` is emitted as the `audience` query parameter on `authorize-url`** — it is the Auth0/Okta-authorization-server parameter for API-audience access tokens and is what a deployment that sets it means. Fixed emission order, so the URL stays byte-pinnable: the eight fixed parameters; then config-derived in this order `audience`, `prompt`, `acr_values`, `ui_locales`, `login_hint`; then `max_age` from the request; then caller extras in input order. `login-hint` is documented at `oidc.md` §3.1 (:90) beside the others. Spec text to change: `oidc.md` §3.1 (`login-hint`, `audience` semantics), §3.2 (`refresh` and `opts.previous`), §4 (the emission order). **Flagged: spec text changes, delegated G3.**

## 1404-a — an unrecognized `<Condition>` INVALIDATES; `OneTimeUse` and `ProxyRestriction` are recognized; `AuthnStatement` and `@Version` are read

- **(a) refuse any `Conditions` child or attribute the module does not evaluate; recognize the three the Web SSO profile uses; project `AuthnStatement` onto the JWT claim names; check `@Version`.** DELETES: acceptance of assertions carrying an unknown condition — which SAML Core §2.5.1.1 says MUST be rejected. Rejects assertions we accept today, and that is the point.
- **(b) ignore unknown conditions and document it.** Contradicts the normative text verbatim ("An assertion that is determined to be Invalid or Indeterminate MUST be rejected"). Refused.
- **(c) refuse unknown conditions but keep `AuthnStatement`/`@Version` unread as a recorded non-goal.** Leaves the IdP's own session bound (`SessionNotOnOrAfter`) discarded on a login surface, which is the one piece an enterprise security review asks about first. Refused.

**Ruled (a), item by item:**

1. **Unrecognized `Conditions` child ⇒ `CXER5406`**, naming the element ("SAML Core §2.5.1.1 rule 3 — a condition this service provider does not understand makes the assertion Indeterminate, which MUST be rejected"). Recognized children: `AudienceRestriction` (evaluated), `OneTimeUse` (Valid), `ProxyRestriction` (Valid). An abstract `<Condition xsi:type=…>` is unrecognized by construction. Any attribute on `Conditions` other than `NotBefore`/`NotOnOrAfter` ⇒ the same refusal (rule 3 covers attributes).
2. **`OneTimeUse` is recognized and evaluates Valid** (the normative text: the assertion "SHOULD be used immediately … and MUST NOT be retained" — a constraint on the relying party's caching, never a validity failure). It is SURFACED so the replay store (#1405) can act: `claims` gains **`jti` ← `Assertion/@ID`** (the JWT replay identifier — the natural mapping, and it is the identifier #1405 says is unreachable on the path a deployment uses) and a `[payload]` key `one_time_use: true` when the element is present.
3. **`ProxyRestriction` is recognized and evaluates Valid.** It restricts a relying party that RE-ISSUES assertions; this service provider issues none, so the restriction is satisfied trivially. Recorded in `saml.md` §1.1.
4. **`AuthnStatement` is read and projected onto the JWT names the platform already consumes:** `SessionNotOnOrAfter` ⇒ `exp` becomes the EARLIER of `Conditions/@NotOnOrAfter` and `SessionNotOnOrAfter` (a session must end at the earlier bound; JWT `exp` is exactly "do not accept after"); `AuthnInstant` ⇒ `auth_time`; `AuthnContextClassRef` ⇒ `acr`. Because session derives its expiry from `exp`, the IdP's session bound is enforced with no new session code, and `acr` reaches `authz` policy the same way an OIDC `acr` does.
5. **`@Version` must be present and equal `"2.0"`** on the document element (in `verify`, step 1) and on the `Assertion` (in `assertion`); anything else is `CXER5400` — `saml.md` §7 already words 5400 as "well-formed XML that is not a SAML 2.0 Response/Assertion".
6. **`Advice` is not read**, recorded as a decision (SAML Core: relying parties MAY ignore it).

Spec text to change: `saml.md` §1.1 (ProxyRestriction, Advice), §4.5 (conditions rule, AuthnStatement, Version), §4.6 (the three new claims), §7 wording. **Flagged: spec text changes, delegated G3.** Conformance: one arm per new refusal and one positive arm per projection.

## 1408-a — `out-err` pins the TOP-LEVEL code in ONE shared matcher; a `[cause]` is pinned by an explicit `cause=` token; oidc stops borrowing the panic converter, and a capability denial propagates as `CXER0271`

### 1. The word `panic`

`mk_err_with_cause` is the §9.2 postfix-panic converter; its `'panic'` message is correct THERE and wrong everywhere else. **Ruled: oidc stops calling it.** A transport fault is wrapped as `[err code=CXER5300|CXER5306 message='E_OIDC_…: <what failed> — <the cause's message>' [cause …]]` — a real message with the cause's text in it, and the cause still chained. `mk_err_with_cause` stays what it is; no other module calls it for wrapping (grep at landing, and a lint-shaped test that refuses a new caller outside the boundary converters).

### 2. The capability-denial contract

`oidc.md` §8 (:225) and §9 say `discover`/`refresh`/`complete`/`client-credentials` without `net` **raise `CXER0271`**. The spec is right and the implementation wraps. **Ruled: a transport result whose code is `CXER0271` propagates UNCHANGED as the top-level value** — the same rule crypto's `CXER3711` gets at `oidc.md:222` ("this module does not restate crypto's answers"). No spec change.

### 3. The matcher — the widest blast radius in the tree

- **(a) `out-err` with a `cx-err:CXERnnnn` token pins the TOP-LEVEL `code` of the rendered err — equality, not containment; a `cause=cx-err:CXERmmmm` token in the same body pins the code of a `[cause]` descendant; a body with no CXER token keeps whole-string containment over the top-level message; the thrown path (R3.12) is unchanged, a V error has no structure. ONE `out_err_matches(rendered, out_err)` function in `vcx/code`, called by every runner** — `code_eval_fixtures_test.v` (both loops), `profile_gate.v`, `conformance_run.v`, `fmt_conform.v`, `code_parse_fixtures_test.v` — replacing five private copies. DELETES: the ability of an `out-err` case to pass on a wrapped error with a different top-level code. Every case that flips red under the new matcher is a FINDING and is classified at landing — either the implementation's top-level code is wrong (fix the code) or the wrap is by design and the fixture was pinning the cause by accident (rewrite the fixture to `<band> cause=<inner>`); the landing note lists every flipped case with its class. Nothing is trued silently.
- **(b) keep containment, add a lint that flags out-err bodies whose token is not the top-level code.** A lint over 1325 bodies that only warns is (a) with the enforcement removed. Refused.
- **(c) pin the top-level code and make the `[cause]` pin a separate `out-err-cause` section.** A second section for one assertion; the cause is part of the same expectation and belongs in the same body. Refused for the same reason `parse-callback` was refused in oidc: surface without capability.

**Ruled (a).** The memory `reference_out_err_pins_only_the_code` records the other half of this hole (a band-only fixture pins the band, never the wrap) and its workaround, the out-text pair-reading idiom (`session-065`); the `cause=` token is that idiom made declarative, and the idiom stays legal.

Blast radius measured before ruling: 1325 bodies, ~1285 bare `cx-err:CXERnnnn` lines. Most already name the top-level code (the case author recorded what the binary rendered, which is the top-level code when nothing wraps). The flips are exactly the wrapped ones, which is the population this issue exists for.

## 1409-c — the shape of the `client_secret_jwt` exception, decided detail by detail

**Fable, 2026-09-11, under the same delegation.** 1409-a is the owner's: the
method lands and the HS exception is scoped to client assertions. What follows
is the implementation shape that scoping needs, ruled here so the landing has
something to be measured against rather than inventing it commit by commit.

1. **Spelling.** `[client-auth method=:secret-jwt secret="…"]` — the fifth
   method, beside `:secret-basic`, `:secret-post`, `:private-key-jwt` and
   `:none`. The atom is `:secret-jwt` and not `:client-secret-jwt`, because
   every other method already drops the `client_` the RFC spells: the element
   attribute is `method=`, so the word is already there.
2. **The assertion is `private_key_jwt`'s, key and algorithm apart.** `iss` =
   `sub` = client id, `aud` = the token endpoint, a `jti` drawn per call, `iat`
   and `exp` from the `now` the verb was handed — RFC 7523 §2.2 — sent as the
   same `client_assertion` / `client_assertion_type` form pair. The two arms
   stand side by side in one function so the difference between them is
   readable as one line rather than as two code paths.
3. **The signing path is PRIVATE to `cx-stdlib/oidc` and calls crypto's HMAC
   primitive directly.** It is not reachable through `crypto:jwt-sign`'s public
   alg set, and `crypto:jwt-verify`'s allow-list is untouched. This is the
   whole of what "scoped to client assertions" can mean in code: if the
   exception lived in `jwt-sign`, every caller of the public JOSE surface would
   have it, and J-4 would be a comment rather than a rule.
4. **`alg=` other than `HS256` is `CXER5307`.** The exception is exactly one
   algorithm on exactly one token; a `[client-auth]` asking for `HS512` is
   asking for a wider exception than was granted, and the refusal says so.
5. **The paired conformance case is part of the landing, not a follow-up.** A
   case asserting an `HS256` **ID token** is still refused with crypto's own
   `CXER3713` lands in the same commit as the method. Without it the corpus
   would record that oidc gained `HS256` and record nothing about how narrowly,
   and the next reader would widen it in good faith.
6. **`random` is charged on the branch, not on the verb.** `secret-jwt` draws a
   fresh `jti` exactly as `private-key-jwt` does, so it joins that guard —
   `complete` / `refresh` / `client-credentials` stay `net`-nominal and a caller
   using `:secret-basic` is not charged for entropy it never consumes.
7. **The interop lane grades the assertion over a real socket.** The in-tree
   identity provider gains a `jwt-secret-client` registration and verifies the
   assertion the way an identity provider has to — recomputing the MAC with
   `crypto:hmac-verify`, because `crypto:jwt-verify` refuses `HS*` and must go
   on refusing it. That the two halves of the lane need different verbs is the
   clearest statement of the exception's shape that the tree can make.
