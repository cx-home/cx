### DSC-1a — the SVG carrier belongs inside the root element

**The measured violation** (live, this head, graphviz 14.1.3):

```
$ cx diagram p.cx --format=svg -o out.svg
$ xmllint --noout out.svg
out.svg:3: parser error : Extra content at the end of the document
<!DOCTYPE svg PUBLIC "-//W3C//DTD SVG 1.1//EN"
^
```

`inject-svg-metadata` splices after the first `>` in the document. On
real graphviz output that `>` closes the `<?xml …?>` declaration, so
the emitted document is:

```
<?xml version="1.0" encoding="UTF-8" standalone="no"?>
  <metadata><cx:source …>…</cx:source></metadata>     ← in the PROLOG
<!DOCTYPE svg PUBLIC …>                               ← after an element
<!-- Generated by graphviz … -->
<svg …>…</svg>                                        ← a SECOND root
```

Two clauses of XML 1.0 §2.1 are broken at once. `document ::= prolog
element Misc*` admits exactly ONE element at the top level, and
`prolog ::= XMLDecl? Misc* (doctypedecl Misc*)?` admits no element
before the doctype. The parser therefore takes `<metadata>` as the
document element and reports everything from the DOCTYPE onward —
including the entire real drawing — as extra content. The rendered
SVG has never been a well-formed XML document.

**Where the carrier belongs.** SVG 1.1 §5.10 makes `metadata` a
description element admitted as a child of `svg`; the conventional
position is first child of the root. That is the one position that is
valid, keeps the carrier inside the document it describes, survives
every SVG consumer's parse, and needs no change to the extractor.
**Ruled:** `inject-svg-metadata` inserts the block immediately after
the root `<svg …>` START TAG, i.e. as the root element's first child.

The start-tag end is located quote-aware (a `>` inside a single- or
double-quoted attribute value does not end the tag — XML 1.0
`AttValue`), and a self-closing root (`<svg …/>`) is opened into a
container so the child has somewhere to live. No `<svg` in the input
is still a pass-through, exactly as before.

**Round trip is untouched.** `extract-svg` scans for `<cx:source`
anywhere in the document and slices between the tag's `>` and
`</cx:source>`; the carrier's bytes and the base64 payload are
identical, only its position moves. Gate 9's byte-for-byte recovery
holds by construction and is asserted directly.

**Golden movement is the fix.** `vcx/tests/testdata/diagram_vector_golden/splice.svg`
regenerates in the same commit. It is the ONE golden that moves. The
before form fails `xmllint --noout` with the error quoted above; the
after form passes. `envelope.svg` does NOT move — the dot-less
envelope already placed `<metadata>` inside `<svg>` and already
parsed clean; that it did is the strongest evidence the splice was the
outlier and not the contract.

**Validity becomes a gate, never a one-time fix.** The vector lane
gains a case that parses every emitted SVG form with the engine's own
XML reader — the envelope, the fixed-input splice, and a splice over a
GRAPHVIZ-SHAPED input (XML declaration + DOCTYPE + comments + root
element: the exact shape that produced the defect) — and asserts each
one round-trips the source byte-for-byte after parsing clean. The
pre-fix bytes fail this case, so the defect cannot silently return.

### DSC-1b — PNG is CLEAN; no analogous defect

Checked, not assumed. The `tEXt` splice was walked chunk by chunk on a
live `cx diagram --format=png` rendering:

```
IHDR  len=13    crc=OK
tEXt  len=102   crc=OK   keyword='cx-source'  → decodes to the exact source
bKGD  len=6     crc=OK
IDAT  len=8192  crc=OK
IDAT  len=1962  crc=OK
IEND  len=0     crc=OK
```

Every CRC-32 verifies, `IHDR` is first, `IEND` is last, and `tEXt` is
an ancillary chunk that RFC 2083 §4.2.3 admits anywhere between them —
after IHDR is a legal and conventional position. A real decoder reads
the file (`sips`: 130×443). The PNG path is correct as shipped and is
NOT touched by this ruling; only its capability behavior changes under
DSC-1c.

### DSC-1c — the graphviz formats require an explicit grant

**Ruled:** `svg`/`png` — the two formats that invoke `dot` — now
REQUIRE the `subprocess` capability from the caller. `cx diagram`
stops granting it to itself.

- **The flag is `--allow-subprocess`** — the established CLI grant
  vocabulary (`--allow-<cap>` over `code.capability_names()`, which
  already carries `subprocess`), not a new flag shape. The broad
  grants `--allow-common` and `--allow-all` include it and are
  accepted for the same reason they are accepted everywhere else. A
  misspelled `--allow-…` on `cx diagram` is a hard error naming the
  accepted set, matching `main.v`'s §3.7 rule.
- **Refusal is LOUD and typed, never a fallback.** Without the grant
  the command refuses with `cx-err:CXER0271` / `E_CAP_DENIED`, naming
  the capability AND the exact flag, and exits non-zero. Silently
  substituting the 1×1 envelope for a user who asked for a rendered
  diagram is the behavior this ruling exists to end.
- **`dot` being ABSENT is a DIFFERENT condition and keeps the
  envelope.** A granted caller on a machine with no graphviz — or a
  non-zero `dot` exit, or a spawn failure — still gets the dot-less
  envelope, which is still the named normative contract of §6. The
  module distinguishes the two by the err code the effect point
  returns: `CXER0271` (denial) refuses; `CXER4001`/`CXER4000`/
  `CXER4003` and a non-zero exit take the envelope road.
- **This is the MODULE's contract, not the CLI's.** The distinction
  lives in `cx-stdlib/diagram`'s `render-svg`/`render-png`, so every
  caller — `cx diagram`, `cx eval --target=svg`, the ABI, an embedding
  host — behaves the same way. `[?fallback … [recover-with …]]`
  replaces the `[?else]` coalesce so the err is INSPECTED rather than
  discarded; C14's requirement (the denial must not propagate
  railway-style out of the binding) still holds, because the recovery
  body converts it to a value the caller's own `[?if]` decides on.
- **Mermaid is unaffected** — pure text, no capability, no flag.

This overturns §6's "**Every** such reason takes this one road"
sentence and §7's first bullet in `spec/03-approved/std-lib/diagram.md`;
both are rewritten with this ruling.

**Both roads are pinned.** Gate 9 gains a capability-withheld case
asserting the typed refusal, and re-pins the dot-less road under the
condition that now actually produces it — `subprocess` GRANTED with
`dot` unreachable (PATH stripped for the duration) — so the envelope
contract is tested by its real cause rather than by a denial.

### Live verification (beyond the gates)

- `cx diagram p.cx --format=svg` with no grant → the CXER0271 refusal,
  exit 1; with `--allow-subprocess` → a real graphviz SVG that passes
  `xmllint --noout` (RC 0); with `--allow-common` → likewise.
- `PATH=/tmp/no-graphviz-here cx diagram … --format=svg
  --allow-subprocess` → the 1×1 dot-less envelope, exit 0.
- `--format=png` behaves identically; the rendered PNG still walks
  clean (all CRCs, keyword `cx-source`, payload = the exact source).
- `--format=mermaid` unchanged and still capability-free.
- `--allow-subproc` (misspelled) → hard error, exit 2, listing the
  accepted grants.

### Noted, not changed

The carrier declares `xmlns:cx="https://cx.lang/v1"`, which re-binds
the `cx` prefix that CX's OWN XML reader reserves (`cx.parse_xml`
refuses it with E213). That is a CX-document policy, not an XML or SVG
rule — the emitted SVG is valid to every XML parser — so it is out of
DSC-1's scope and left alone. It is why the new validity gate checks
the XML 1.0 §2.1 clauses directly instead of round-tripping through
`cx.parse_xml`.
