# Decisions, 2026-09-13 — the formatter's cost (#1433)

Taken by the integrator under the owner's delegation. The id is the one cited in commits.

| Id | Decision |
|---|---|
| **1433-a** | **`cx fmt` is profiled on the 8k-record bench document and its redundant passes are folded, inside what `formatting.md` §7 already says — no spec sentence moves.** (1) A profile names every pass and its share — the data-lane parse, the program parse, the width-bounded layout, the comment placement, the emitter, the §1 tree comparison, the §7 verification, the structural fingerprint — measured hot, three readings each, recorded in the branch's `RESULTS.md` and on the issue. (2) The folds are of REDUNDANT WORK ONLY: the same parse, emit or fingerprint computed twice over bytes already in hand. The width-bounded layout, the §1 tree guard (formatting.md §7 (a): the formatter re-parses its own output and compares that node tree to the input's) and the §7 verification are NOT dropped, and no verdict changes — `conformance/fmt.cxd`, the fmt guard tests and `make fmt-sweep-gate`'s FORMATTED / DECLINED / TREE-REFUSED counts are identical before and after. (3) Target: `tooling.fmt_8k_ms` at or under the v0.17.0 number plus 10 % (≤ 710 ms) hot; the landing re-pins that one row of `bench/baseline.json` to its own hot measurement, so the final `v0.18.0` cut's ratchet (1249-Q1a) holds the improvement — a ratchet number goes down only. Why: INT-6 re-pinned the row to 1.77 s so the pre.1 cut could proceed and named this issue as the fold for the final cut; the cost is deterministic (three readings within 1 %), not load. |
| **1433-b** | **What §7 requires, read literally, is the RE-PARSE AND TREE COMPARISON, not a second format.** §7 (a): "the formatter re-parses its own output and compares that node tree to the input's — node kinds, node order, text values after entity decoding, and each attribute's typed value". The word idempotence does not appear in `formatting.md`; `fmt(fmt(x)) == fmt(x)` is #1330's own guard, and #1330's reason for it stands on its own (an unstable formatter makes the LSP rewrite the file on every save). So: the §7 tree comparison stays exactly as specified and is what the spec text governs; the #1330 fixed-point guard stays as a PROPERTY and is free to be established by any sound means. A fold that would weaken either the tree comparison or the fixed-point property is out of scope here, and the shortfall would be a flag rather than a spec edit. |
| **1433-c** | **A pass computed twice over the same bytes is computed once and passed down.** The seam this creates is a private one — `fmt_source_outcome` hands the lane the parsed readings it already holds — and every verification keeps its own independent subject: the §1 tree guard still compares two separately parsed node trees (input's and output's), and the fixed-point guard still asks whether re-formatting the candidate settles on it. Reuse of a PARSE is not reuse of a COMPARISON. |
