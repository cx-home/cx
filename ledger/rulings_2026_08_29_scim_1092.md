# Rulings — SCIM 2.0 provisioning surface (#1092)

2026-08-29, release/0.18. Campaign umbrella #1097, workstream C. Recorded
BEFORE the work.

## C-0 — what is actually hard here

Worth stating first, because it drives every letter below. The difficult,
reusable part of SCIM is **not** the HTTP. Routing `/Users` and `/Groups`
is a handful of lines against the existing http surface, and it is
exactly where a deployment wants control — its own auth, tenancy, paths
and rate limits.

The hard part is the **semantics**: RFC 7644 §3.5.2 PATCH operations over
multi-valued attributes with value-filter paths, the §3.4.2.2 filter
grammar, case-insensitive attribute matching, and the canonical resource
shapes. That is what every SaaS built on CX would otherwise reimplement,
subtly differently, and get wrong in the same places everyone gets it
wrong.

## C-1 — shape (RULED: C-1 = a)

- (a) **A pure `cx-stdlib/scim` module of SCIM SEMANTICS**; the feature
  mounts its own routes. TAKEN.
- (b) A mounted service the feature attaches — rejected. It would weld
  the module to one auth model, one tenancy model and one URL layout, and
  every precedent in this tree splits codec from transport: `zip` and
  `tar` are codecs, `crypto` §3.10 verifies rather than running flows,
  and `oidc` leaves the redirect to the caller.
- (c) Both — rejected for v1: the mounting half is small, and building it
  before a feature needs it is a seam with no live consumer.

**The module stores nothing** and knows nothing about the principal model
— the oidc O-3 posture. Mapping a SCIM resource onto a store principal is
the feature's job, because CX cannot know a deployment's user model. What
the module guarantees is that the resource it hands over is a faithful,
validated reading of what the IdP sent.

## C-2 — v1 scope (RULED: C-2 = a)

In: **Users** and **Groups** core schemas plus the enterprise-user
extension; **PATCH** semantics; the **full** filter grammar (C-4); the
`ServiceProviderConfig` / `ResourceTypes` / `Schemas` discovery documents
as values; the `ListResponse` envelope; and the SCIM error object shape.

Out, with reasons rather than silence: **bulk operations** (RFC 7644
§3.7 — no IdP in the target set sends them by default), **`/Me`**,
sorting, and the SCIM **client** half. The client half is explicitly
"only if a consumer appears" in the issue, and that is the
seam-needs-live-consumer rule agreeing.

## C-3 — PATCH is a PURE function, and it is the crown jewel (RULED: C-3 = a)

`apply-patch(resource, operations) -> resource`. Pure, total, no I/O.
That is what makes the subtle part testable at all, and it is why this
module is worth having.

The RFC's genuinely tricky corners, each of which gets a fixture:

- `add` to a multi-valued attribute **appends**; `add` to a single-valued
  attribute **replaces**. Same verb, different meaning by target arity.
- `replace` with **no** `path` merges the given attributes into the
  resource, rather than replacing the resource.
- A `path` may carry a **value filter** — `members[value eq "x"].display`
  — selecting members to operate on, and `remove` with such a path
  removes matching members rather than the attribute.
- Attribute names are **case-insensitive**; `userName` and `username`
  address the same attribute.
- `remove` of an absent attribute is a **no-op**, not an error.

**Where the RFC is ambiguous, the reading the major IdPs actually send
wins, and the fixture says which behaviour it is pinning and why.** That
is the honest posture: an interoperability surface that follows a strict
reading nobody sends is correct and useless. Every such case is marked in
the corpus, so a future reader can tell a deliberate interop choice from
an accident.

## C-4 — the FULL filter grammar (RULED: C-4 = a)

- (a) **The whole of RFC 7644 §3.4.2.2**: `eq ne co sw ew gt lt ge le pr`,
  `and` / `or` / `not`, grouping, and value paths. TAKEN.
- (b) The `eq` + `and` subset the issue floats as a minimum — rejected. A
  recursive-descent parser for the full grammar is small, and a subset
  invites "why does `or` not work" forever. Partial implementations are
  the thing this project refuses everywhere else; the grammar is not big
  enough to be the exception.

Filters parse to a VALUE, and matching is a separate pure verb over a
resource. A deployment that wants to push a filter down into its own
store can walk the parsed value instead of the string — which is the
whole reason to return a value rather than a predicate.

## C-5 — bearer-token auth is NOT in this module (RULED: C-5 = a)

An IdP authenticates to the SCIM endpoint with a bearer token, and that
is `crypto:jwt-verify` plus `session`, already built. Re-exposing it here
would be a second door to the same room. The module's verbs take an
already-authenticated request's body; who is calling is the feature's
question, answered with machinery that exists.

## C-6 — schema extension is data, not code (RULED: C-6 = a)

The enterprise-user extension ships as a known schema, but the validator
is driven by schema VALUES, not hard-coded field lists. A deployment with
a custom extension supplies its schema and gets validation without
patching the module. This is the one place SCIM's design is genuinely
good and it would be a waste to flatten it into a struct.

## C-7 — error band (RULED: C-7 = a)

**`CXER5600–5699` allocated to `cx-stdlib/scim`** — the next free
hundred-block above tar's `5500–5599`. Band-scan to confirm at
registration; the row lands in `governance.md` §9.6 first, that table
being the registry.

The **#1100 rule applies here too**: malformed vs unsupported tracks
whose fault it is. A PATCH op with an unparseable path is the sender's
fault (malformed); a `bulk` request is a valid SCIM operation this module
declines (unsupported). Classify every refusal by that test.

## C-8 — the SCIM error object (RULED: C-8 = a)

SCIM defines its own error body (`scimType`, `detail`, `status`). The
module RETURNS that shape as a value for the feature to serialize; it
does not invent a CX-shaped error for a protocol that specifies one.
CXER codes remain the in-process channel — the two do not compete,
because one crosses the wire and the other does not.
