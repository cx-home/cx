# Ruling record — #1226 / #1119 RP-5: the exit bar is RSS ÷ LIVE at parse peak, not RSS ÷ input (2026-09-05)

Issue: #1226 (closed 2026-09-04 @ e105956f0 for the CX-side cause). Campaign: #1119 (RP-5).
Runtime half: cx-home/v#6, mirror #1295 (`upstream`).

## The question, restated in one line

RP-5(a)(i) set campaign exit at **peak RSS ≤ 8× input**. The live tree ALONE is 7.6× input
on the json audit corpus, and vgc's documented pacing goal is 2× marked, so the floor is
≈15× input before a single retained span. The bar is unreachable by construction and says
nothing about the thing that regressed.

## RULED (a) — re-base RP-5 to **RSS ÷ live ≤ 2.5× at parse peak**

Recommended on the issue and accepted under the standing letter rule.

- Measures what the runtime controls — pacer goal + span-pool retention — independently of
  how dense the representation is. RP-6's concern (live density) and the collector's concern
  (multiplier over live) stop being one number.
- Current json lane: **3.7×**. The bar therefore stays RED until cx-home/v#6 (the span-pool
  trim that never fires on a monotone build-up) lands. That is the honest state and the
  reason to prefer it: it keeps a real ratchet instead of recording a pass.
- **DELETES:** the `peak RSS ≤ 8× input` formulation of RP-5(a)(i), and with it the reading
  that #1119's representation work could ever have satisfied it.

Rejected, restated for the record:
- (b) `peak RSS ≤ 40× input` — passes today at 36×, but it is a number fitted to one
  measurement; it drifts with every representation change and stops meaning anything the
  moment RP-6 changes live density.
- (c) keep ≤ 8× input and gate on RP-6 + cx-home/v#6 — even RP-6's modelled 2.4× live under a
  perfect 2× pacer is ≈5× input, so the bar would gate on both and still conflate the two
  causes this issue exists to separate.
